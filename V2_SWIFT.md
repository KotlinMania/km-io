## 1. Architecture Overview & Core Acceptance Invariants

Kotlin/Native Swift Export translates compiled Kotlin/Native `.klib` modules into:
1. **Generated Kotlin/Native `@ExportedBridge` wrappers** (`build/SwiftExport/<target>/<config>/.../*.kt`), which are compiled by `compileSwiftExportMainKotlin<Target>` and linked with the main KLIB into a static library (`libSwiftExportBinary.a` $\to$ merged `lib<ModuleName>.a`).
2. **Generated C bridge headers and Clang `module.modulemap` files** (`build/SPMPackage/<target>/<config>/Sources/SharedBridge_<Module>/include/*.h` plus `KotlinRuntime/include/KotlinBase.h` and `KotlinCoroutineSupport.h`).
3. **Generated Swift modules and a SwiftPM `Package.swift` manifest** (`build/SPMPackage/<target>/<config>/Package.swift` and `Sources/<Module>/*.swift`), which are compiled by `xcodebuild` during `macosArm64DebugBuildSPMPackage` / `embedSwiftExportForXcode` and consumed by the repository's `src/swift/swift-test-harness`.

### Non-Negotiable Acceptance Invariants

- **Distinct compilation gates:**
  - **Kotlin/Native Bridge Gate:** `compileSwiftExportMainKotlinMacosArm64` must compile with `allWarningsAsErrors = true` (`-Werror`). Scoping `allWarningsAsErrors = false` to `compileSwiftExportMain*` or injecting post-generation `@file:kotlin.Suppress(...)` headers into generated `.kt` files is **not** an accepted production gate.
  - **Swift Dependency Gate:** Generated Swift dependency modules (`KotlinRuntimeSupport`, `KotlinCoroutineSupport`, `ExportedKotlinPackages`, `KotlinStdlib`, and exported library modules) compile in **Swift 5 language mode (`-swift-version 5`)** with **`-warnings-as-errors`** (`SWIFT_TREAT_WARNINGS_AS_ERRORS = YES`) and Clang `GCC_TREAT_WARNINGS_AS_ERRORS = YES`.
  - **Swift Consumer Gate:** Hand-authored Swift consumer test modules (`SwiftTestHarnessTests`, `<Module>ConsumerTests`) compile in **Swift 6 language mode (`-swift-version 6`)** with **`-warnings-as-errors`** targeting `arm64-apple-macosx15.0`.
- **Zero executed tests is never acceptance:** A green Gradle or CI job label with `0` executed Swift test cases (or skipped/import-only tests) is a failed gate. Every acceptance report must record the exact final commit SHA, effective per-module compiler flags, and positive executed test counts across each runtime.
- **No public API hiding, no unsafe concurrency promises, no installed SDK mutations:**
  - Never hide primary exported APIs with `@HiddenFromObjC` or `internal` merely to dodge bridge warnings.
  - Never add `@unchecked Sendable` or `@preconcurrency import` to silence Swift 6 concurrency diagnostics.
  - Never mutate shared or installed Kotlin/Native distributions under `~/.konan`; select any required header repair exclusively via a project-local SDK copy passed through `-Pkotlin.native.home=<prepared-sdk-path>`.

### Retired Legacy Recipes (Do NOT Follow in Active Work)

Selective readers of historical sections in [`SWIFT.md`](file:///Volumes/stuff/Projects/kotlinmania/template/SWIFT.md) must **never** copy these retired early-rollout patterns:

1. **Retired `iosX64` (and all Apple `x86_64` / 32-bit targets):** `iosX64`, `macosX64`, `tvosX64`, `watchosX64`, `watchosArm32`, `watchosArm64` (`arm64_32`), `androidNativeArm32`, `androidNativeX86`, `linuxArm32Hfp`, and `mingwX86` are permanently retired (`AGENTS.md` §5.5). Only `iosSimulatorArm64` (with `isStatic = true`) is used for iOS simulator builds.
2. **Retired `XCTAssertTrue(true)` import-only smoke tests:** An import-only test that asserts `true` does not exercise any generated Swift symbol or C bridge symbol and is rejected under the completion contract.
3. **Retired automatic PR-triggered CI assumption:** Top-level `ci.yml` uses `workflow_dispatch:`, reusable platform workflows (`swift.yml`, `macos.yml`, `ios.yml`, `linux.yml`, etc.) use `workflow_call:`, and `publish.yml` uses `release` (`published` / `released`) plus `workflow_dispatch:` — none use `push:` or `pull_request:`. Opening a PR does not automatically trigger CI; run `./gradlew build` and `./gradlew test` locally first, then trigger at most one `gh workflow run` per 5-minute window when ready.
4. **Retired generic-class hiding with `"no API change"` and public `Pair<A, B>`:** Hiding a public upstream Rust struct (such as `pub struct ZipEq<I, J>`) as `internal class` and widening its factory return type to `Iterator<Pair<A, B>>` **does** change the public API (removing concrete type members) and exposes `kotlin.Pair<A, B>`, which triggers `Unchecked cast of 'Any?' to 'Pair<Any?, Any?>'` in `KotlinStdlib.kt` under `-Werror`. Only mark declarations `internal` when the upstream Rust declaration is genuinely crate-private (`pub(crate)` or private, as verified for `IsolateAnnex.slots` in `v8-kotlin`).
5. **Superseded "snapshot-mandatory" (`DELIVERY.md`) and "source-compatible-unbuilt" (`dbfc468a`) checkpoints:** Removing `KotlinError.wrapped` is **not** mandatory, and the source-compatible `dbfc468a` candidate is no longer unbuilt — it has been packaged (`32f6c1ac...` + `99186d1d...`) and verified at `db24b93` / `70d733a` ([`DELIVERY_CURRENT.md`](file:///Volumes/stuff/Projects/kotlinmania/syn-kotlin/verification/swift-exporter-patches/syn-library/DELIVERY_CURRENT.md)).

## 2. Compiler Version vs. Manifest `swift-tools-version` vs. Per-Module Language Modes (`5` vs `6`)

Three version settings govern Swift compilation and **must never be conflated**:

| Setting | Where Specified | Role & Default Behavior under Swift 6.3 (`swiftlang-6.3.3.1.3`) |
| :--- | :--- | :--- |
| **1. Swift Compiler Version** | Host toolchain (`xcrun swiftc --version`, e.g., `Apple Swift version 6.3.3` in Xcode 26.6) | Determines the compiler binary, parser syntax support (`sending`, `nonisolated(nonsending)`), and diagnostic rules available. Does **not** by itself set `-swift-version 6` on every package target. |
| **2. SwiftPM Manifest `swift-tools-version`** | Line 1 comment of each `Package.swift` (`// swift-tools-version: 5.9` vs `// swift-tools-version: 6.0`) | Controls the `PackageDescription` API version AND the **default** Swift language mode for targets in *that specific package* when `swiftLanguageModes` is omitted (`5.9` $\to$ defaults targets in that package to `-swift-version 5`; `6.0` $\to$ defaults targets in that package to `-swift-version 6`). **A `swift-tools-version: 6.0` consumer harness does NOT force a path-dependency package with `swift-tools-version: 5.9` into `-swift-version 6`.** |
| **3. Effective Per-Module Language Mode (`-swift-version`)** | Passed to `swift-frontend` per module via `Package.swift` `swiftLanguageModes: [.v5]` / `[.v6]`, Xcode `SWIFT_VERSION = 5` / `6`, or CLI `-Xswiftc -swift-version -Xswiftc <N>` | Controls whether strict Swift 6 concurrency checking (`#SendableClosureCaptures`, `Sendable` stored-property enforcement) is enforced as hard errors on that module. **Warning:** Passing `-Xswiftc -swift-version -Xswiftc 6` on the `swift test` CLI overrides *every* dependency target in the graph simultaneously. |

### Does Kotlin 2.4.20 or 2.4.21 Gate Generation on Swift `< 6`?

**No Swift-version gate exists in the inspected generation call chain or audited compiler archives.** Bytecode disassembly (`javap -c -p -v`) and entry-by-entry archive SHA256 verification ([`javap-2.4.20-vs-2.4.21.json`](file:///Volumes/stuff/Projects/kotlinmania/automation-artifacts/2026-10-20-async-trait-swift-mode-diagnostic/javap-2.4.20-vs-2.4.21.json), `SHA256: c428af050d775f702c4147803e60183da1be7b2d482b2d8cc3e2842b1017e1ea`) establish across the inspected KGP/exporter call path (`SwiftExportTask` $\to$ `SwiftExportAction` $\to$ `SwiftExportRunnerKt.runSwiftExport` and `GenerateSPMPackageFromSwiftExport`) that:

1. **Zero Swift-version branches in the inspected generation call chain (`SwiftExportTask` $\to$ `runSwiftExport`):** `SwiftExportTask` $\to$ `SwiftExportAction` $\to$ `SwiftExportRunnerKt.runSwiftExport` (`SwiftExportConfig` + `SwiftModuleConfig`) accepts only KLIB paths, `outputPath`, `stableDeclarationsOrder`, `renderDocComments`, `enableCoroutinesSupport`, `distribution`, `konanTarget`, `errorTypeStrategy`, `unsupportedTypeStrategy`, and `logger`. Nothing in that inspected invocation chain queries `swiftc` or checks a Swift language or compiler version (this finding is scoped to the inspected `swiftexport` / `sir` call chain and archive audit, not an uninspected claim over every unrelated compiler subsystem).
2. **Kotlin `2.4.20` and `2.4.21` Swift Export bytecode are 100% identical:**
   - Between `swift-export-embeddable-2.4.20.jar` (`SHA256: 24c6159bcf0087ecf86bfc9bad01a975e192abcf75005b248292d85a139c2055`) and `swift-export-embeddable-2.4.21.jar` (`SHA256: 615e8a032f47baa15bc6126cbffe707c87069445b215ecce7c4830d13b079180`), **`6,262` of `6,263` entries are byte-for-byte identical** (only `META-INF/MANIFEST.MF` differs; **all `681` `swiftexport` + `sir` class and resource entries are byte-identical**).
   - Between `kotlin-gradle-plugin-2.4.20-gradle96.jar` (`SHA256: 6f49688f2c6715d60f5dc52d4c1ada992ce4bed6053d1bd6e579c9392d7ba0ed`) and `kotlin-gradle-plugin-2.4.21-gradle96.jar` (`SHA256: d0a11912936c8801f1773a47e8fc51835a6ab568d73e4e1d188281955a7f575b`), **all `144` `org/jetbrains/kotlin/gradle/plugin/mpp/apple/swiftexport/*` class entries are byte-for-byte identical**.
3. **Why KGP's stock `GenerateSPMPackageFromSwiftExport` defaults dependencies to Swift 5 & macOS 10.13:**
   - `SPMManifestGenerator.generateManifest` (`GenerateSPMPackageFromSwiftExport.kt:167`) hardcodes `// swift-tools-version: 5.9` and emits `.target(name: ...)` blocks without `platforms:` or `swiftLanguageModes:`.
   - Consequently, when `swift test` compiles the generated `SPMPackage` as a path dependency of `src/swift/swift-test-harness` (`// swift-tools-version: 6.0`), SwiftPM compiles all generated dependency modules with **`-swift-version 5`** while compiling the authored test target with **`-swift-version 6`**, and defaults deployment target to `arm64-apple-macosx10.13` unless `-Xswiftc -target -Xswiftc arm64-apple-macosx15.0` is supplied (required because `KotlinCoroutineSupport.swift:78` calls `withUnsafeCurrentTask(body:)`, which requires `macOS 15.0+`).
4. **Separate qualification of SwiftPM's autogenerated `PackageTests` runner:**
   - When `swift test` builds the test entry-point target (`<PackageName>PackageTests`), SwiftPM invokes `swift-frontend` **without an explicit `-swift-version <N>` flag** (using compiler default while retaining `-warnings-as-errors` and `-target arm64-apple-macosx15.0`).
   - Verification scripts and reports must classify `PackageTests` runner frontends separately (`generated_runner_explicit_mode: false`) rather than either failing a strict `-swift-version 6` regex guard or falsely claiming that the generated runner had an explicit `-swift-version 6` flag.

## 3. Original `KotlinError.wrapped` Contract & Coherent Native Ownership Header (`KotlinBase.h`)

### Why the API-Preserving `KotlinError` Variant (`32f6c1ac`) Supersedes the Snapshot Break (`11da4d91`)

Stock Kotlin 2.4.20 / 2.4.21 `KotlinRuntimeSupport.swift` defines:

```swift
public struct KotlinError: Swift.Error, CustomStringConvertible {
    public var wrapped: KotlinRuntime.KotlinBase
    public init(wrapped: KotlinRuntime.KotlinBase) {
        self.wrapped = wrapped
    }
    public var description: Swift.String {
        return _kotlin_swift_export_runtime_error_message(self.wrapped.__externalRCRef()) ?? "KotlinError(\(self.wrapped))"
    }
}
```

Because `Swift.Error` refines `Sendable` in the Swift 6 standard library while `KotlinRuntime.KotlinBase` is an Objective-C reference class without `Sendable` conformance, compiling `KotlinRuntimeSupport.swift` under **`-swift-version 6 -warnings-as-errors`** rejects `public var wrapped: KotlinRuntime.KotlinBase` (`error: stored property 'wrapped' of 'Sendable'-conforming struct 'KotlinError' has non-Sendable type 'KotlinBase'`).

Two distinct producer candidates were evaluated during the `syn-kotlin` investigation (documented in [`KOTLIN_ERROR_COMPATIBILITY.md`](file:///Volumes/stuff/Projects/kotlinmania/syn-kotlin/verification/swift-exporter-patches/syn-library/KOTLIN_ERROR_COMPATIBILITY.md), `SHA256: cf633dcb167bca214b2d33e248d6a640a3b60c63cd43a2474b61b1a685627022`, and [`DELIVERY_CURRENT.md`](file:///Volumes/stuff/Projects/kotlinmania/syn-kotlin/verification/swift-exporter-patches/syn-library/DELIVERY_CURRENT.md), `SHA256: 92110deb7f5af5a5020afd4e1b9449f2d4e5ba8bbd110ef97048091eee039744`):

### The Two Complementary Runtime Repairs Required by Both Variants

1. **Checked `Throwable` Message Helper (`KotlinRuntimeSupport.kt`):**
   - Stock `KotlinRuntimeSupport.kt` forcibly casts the pointer passed to `_kotlin_swift_export_runtime_error_message` to `kotlin.Throwable`, causing an immediate runtime abort (`ClassCastException`) when `KotlinError(wrapped:)` is constructed with a non-`Throwable` `KotlinBase` instance (reproduced in session `60081`).
   - The repaired `KotlinRuntimeSupport.kt` resource (`syn-kotlin/verification/swift-exporter-patches/ordinary-runtime/KotlinRuntimeSupport.kt.patch`) performs a safe `as? Throwable` check and returns `null` (triggering the Swift `"KotlinError(\(self.wrapped))"` fallback) for non-`Throwable` objects.
2. **Coherent `KotlinBase.h` Retained-Return Ownership Header (`99186d1dd029a8ba5b66dae390a3aec0d6d0e5293eff641d85daab5e212723c3`):**
   - Upstream `ObjCExportClasses.mm` (blob `48c1ab0a73b873e77860cb998f9f36d56f8d6a07` at Kotlin `2.4.20` tag `890ac1d94fdb80eb85f0eeb5be5e4352df987b2f`) returns `+1` retained `alloc`/`init` instances from `createRetainedWrapper:` factory methods, but stock `KotlinBase.h` (`SHA256: 14390b9a40bcd8f924909692249ca95468cd3de36157be762371b1673dab86f3`) omits Clang's `NS_RETURNS_RETAINED` annotation.
   - As verified in SIL dump session `30109`, Swift's Clang importer therefore treats both factory returns as autoreleased (`+0`) and inserts an extra retain, leaking the wrapper across `kotlin.native.runtime.GC.collect()`.
   - Adding `NS_RETURNS_RETAINED` to `konan/swift_export/kotlin_runtime/KotlinBase.h` (`SHA256: 99186d1dd029a8ba5b66dae390a3aec0d6d0e5293eff641d85daab5e212723c3`) aligns the C header declaration with the actual `+1` Native binary implementation without altering any method selector, parameter type, or Native binary.

### B. Consumer Kotlin Public API Hazards, Upstream Visibility Parity & Reviewed Compatibility Migrations

> [!IMPORTANT]
> **No Automatic API Removal — Verify Upstream Visibility, Concrete Operation Parity, and Compatibility First:**
> - **Never** apply `internal`, collection-type replacement, or exception-hierarchy removal as an automatic blanket rule that strips public upstream Rust operations.
> - Before changing any Kotlin declaration's visibility or signature:
>   1. **Check intended upstream Rust visibility (`tmp/`):** Only mark a Kotlin declaration `internal` when the corresponding Rust item is genuinely crate-private (`pub(crate)` or private, such as `IsolateAnnex.slots` in `v8-kotlin`).
>   2. **Verify inherited member bridges on public subclasses:** Marking a generic base class `internal` does **not** automatically eliminate erased bridge casts if a `public` subclass inherits generic methods or properties from that base class (`SwiftExport` still bridges inherited public members).
>   3. **Preserve concrete typed operation parity:** Every public upstream operation must remain callable by Kotlin and Swift consumers with concrete, strongly-typed semantics.
>   4. **Record any signature or type change as a project-specific reviewed migration:** Replacing a generic wrapper, mutable collection view, `Throwable` superclass, `Result<T>`, or backticked keyword spelling changes the public Kotlin/Swift contract and requires explicit compatibility review rather than a claim of "no API change."

1. **Class A — Unconstrained Generic Classes (`Foo<T>`):** Public generic classes erase type parameters to `Any?` (`_KotlinBridgeable`) across the bridge, and public subclasses of an `internal` generic base can still inherit those erased member bridges. **Reviewed remediation:** Only mark a generic helper `internal` if it is crate-private in upstream Rust and no public subclass leaks erased inherited members; for public upstream generic types, preserve concrete typed operation parity via reviewed concrete specializations or strongly-typed facades.
2. **Class B — Uninferrable Generic Functions:** Public generic functions whose type parameter cannot be represented in Swift fail bridge compilation (`Cannot infer type for type parameter`). **Reviewed remediation:** Keep crate-internal generic helpers `internal` while exposing concrete typed public operations matching the upstream API contract.
3. **Class C — Public `MutableList<T>` / `MutableMap<K, V>` / `MutableSet<T>` & Static-Link `ktypew:kotlin.collections.MutableSet` Collision:**
